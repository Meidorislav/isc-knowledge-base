# Ingestion pipeline

Как документы попадают в базу знаний: от загруженного файла до чанков, по которым работает гибридный поиск.

## Принятые решения

| Решение | Почему |
|---|---|
| **Платформа — источник истины.** Существующие страницы wiki импортируются один раз через CLI, дальше документы загружаются только через платформу | Не нужны коннекторы к wiki, расписания и отслеживание удалений в чужой системе. Документ индексируется сразу после загрузки |
| **Один пайплайн, два входа** (CLI и HTTP API вызывают `submit_document`) | Импорт и обычная загрузка гарантированно работают одинаково |
| **Оригиналы файлов хранятся в БД** (`document_versions.raw`) | При смене нарезки или модели эмбеддингов всё переиндексируется без повторной загрузки |
| **Нарезка по структуре с запасным вариантом** | Wiki неоднородна: где-то есть заголовки, где-то сплошной текст. Один алгоритм покрывает оба случая |
| **Эмбеддинги bge-m3** (1024, через Ollama) | Мультиязычная модель, хорошо работает с русским, не требует префиксов. `nomic-embed-text` ориентирована на английский |
| **Настоящий BM25 через ParadeDB `pg_search`** со стеммером `russian` | Встроенный `ts_rank` в Postgres не BM25 (нет IDF и нормализации по длине). `pg_search` — BM25 на Tantivy внутри Postgres, pgvector в том же образе |
| **Очередь задач в Postgres** (`FOR UPDATE SKIP LOCKED`) | Отдельный брокер (Redis/RabbitMQ) не нужен. Один процесс плюс воркер |
| **ACL отложен**, в схеме есть `documents.visibility = 'all'` | Сейчас все видят всё. Колонка заложена, чтобы потом добавить фильтр без миграции данных |

Лицензия `pg_search` — AGPL-3.0. Для внутреннего использования в компании ограничений нет.

## Общая схема

```
 CLI: import ./wiki_export ─┐
                            ├─► submit_document ──► documents + document_versions (raw) + ingestion_jobs
 POST /documents ───────────┘         │                        (одна транзакция)
                                      │
                                      ▼
                        worker: claim_next (SKIP LOCKED)
                                      │
                         parse ─► chunk ─► embed (Ollama bge-m3)
                                      │
                                      ▼
                  DELETE старых чанков + INSERT новых (одна транзакция)
                                      │
                                      ▼
                     chunks: HNSW (pgvector) + BM25 (pg_search)
```

Код: `backend/app/ingestion/`.

| Модуль | Роль |
|---|---|
| `service.py` | `submit_document` — единая точка входа: проверка формата, дедупликация, версия, постановка в очередь |
| `parsing.py` | байты → нормализованный текст; `docx`-заголовки → `#`, таблицы → Markdown |
| `chunking.py` | текст → чанки (**следующий шаг, пока заглушка**) |
| `embedding.py` | батчевые эмбеддинги через Ollama `/api/embed` |
| `pipeline.py` | обработка одной версии документа: parse → chunk → embed → замена чанков |
| `queue.py` | очередь задач на Postgres |
| `worker.py` | цикл воркера, повторы, статусы |
| `cli.py` | массовый импорт папки |

## Жизненный цикл документа

```
uploaded ──► processing ──► indexed
                 │
                 └────────► failed   (ошибка без повтора или исчерпаны попытки)
```

Повторная загрузка (`POST /documents/{id}/versions`) создаёт новую версию и снова ставит документ в очередь. Если задачи завершились не по порядку, более старая версия не перезапишет новую (`pipeline._is_stale`).

## Этапы

### 1. Приём
- Форматы: `txt`, `md`, `docx`. PDF и сканы пока отклоняются с понятной ошибкой (HTTP 415).
- Лимит размера: `MAX_UPLOAD_MB` (по умолчанию 20).
- **Дедупликация** по sha256 от байтов файла: такой же файл отклоняется с HTTP 409 и id существующего документа. CLI просто пропускает дубли, поэтому импорт можно перезапускать.
- Метаданные: `title` (по умолчанию из имени файла), `category`, **`owner`** (обязательно). Ответственный нужен аналитике пробелов: кому отправлять вопросы без ответа.

### 2. Парсинг и нормализация
- Всё приводится к одному формату: текст с Markdown-разметкой там, где структура известна.
- `txt` и `md`: UTF-8, при ошибке cp1251 (старые русские файлы).
- `docx`: стили «Heading N» / «Заголовок N» → `#`×N, таблицы → Markdown-таблицы, порядок блоков сохраняется.
- Нормализация: `\r\n` → `\n`, неразрывные пробелы, хвостовые пробелы, не больше одной пустой строки подряд.

### 3. Нарезка
Один алгоритм, который работает на любом документе:

1. **Поиск заголовков**, от надёжных признаков к эвристикам:
   1. Markdown `#`, уровень по количеству `#`;
   2. нумерация `1.`, `1.2`, `3.2.1 Название`, уровень по количеству чисел;
   3. эвристики: строка короче ~80 символов, без точки в конце, окружена пустыми строками, капс или с заглавной буквы. Строки, начинающиеся с `-`, `•`, `|`, отсекаются (пункты списков и таблицы).

   Заголовки не найдены → весь документ считается одной секцией с путём `[название документа]`.
2. **Для каждой секции**: влезает в лимит — один чанк; длиннее — рекурсивно по абзацам → строкам → предложениям (`razdel`), с перекрытием; слишком короткая — склеивается со следующей секцией того же уровня.
3. **Contextual header**: `search_text = "Документ > Раздел > Подраздел\n\n" + text`. По `search_text` строятся эмбеддинги и BM25, а в LLM и в цитату идёт чистый `text`.

| Параметр | Значение | |
|---|---|---|
| `TARGET_TOKENS` | 500 | целевой размер |
| `MAX_TOKENS` | 800 | верхняя граница |
| `MIN_TOKENS` | 100 | меньше — склеиваем |
| `OVERLAP_TOKENS` | 60 | перекрытие при рекурсивной нарезке |

Токены считаются токенизатором bge-m3. Способ, которым найдена структура, записывается в `chunks.structure` (`markdown | numbered | heuristic | flat`), чтобы на оценке качества было видно, где поиск проседает. При изменении алгоритма поднимается `CHUNKER_VERSION`.

Таблицы не разрезаются посередине: либо таблица целиком, либо построчно с повтором шапки.

### 4. Эмбеддинги
- Ollama `/api/embed`, модель `EMBED_MODEL` (bge-m3), батчи по `EMBED_BATCH_SIZE`.
- Проверяется размерность (должна совпадать с `vector(1024)` в схеме).
- В каждом чанке сохраняется `embedding_model`.

### 5. Запись
В одной транзакции: удалить чанки документа, вставить новые, выставить `current_version_id` и `status = indexed`. Поиск никогда не видит полуобновлённый документ.

## Схема БД

Миграция: `backend/migrations/versions/0001_initial.py`.

```
documents          id, title, category, owner, visibility, status, current_version_id, created_at, updated_at
document_versions  id, document_id, version, filename, file_format, content_hash, raw (bytea), text, created_at
chunks             id, document_id, version_id, ord, heading_path text[], text, search_text, token_count,
                   structure, embedding vector(1024), embedding_model, chunker_version, metadata jsonb
ingestion_jobs     id, version_id, status, attempts, last_error, created_at, started_at, finished_at
```

Индексы на `chunks`:
- `ix_chunks_embedding_hnsw` — HNSW, `vector_cosine_ops`;
- `ix_chunks_bm25` — `USING bm25 (id, (search_text::pdb.simple('stemmer=russian', 'stopwords_language=russian'))) WITH (key_field='id')`.

## Как это используется в поиске

Для контекста, реализация будет в модуле поиска. Гибрид собирается прямо в SQL: топ-N из BM25 (`search_text ||| :query`, скор `pdb.score(id)`) и топ-N из pgvector (`embedding <=> :qvec`) сливаются через **RRF** (Reciprocal Rank Fusion), затем результат отдаётся в bge-reranker.

## Очередь и воркер

- `claim_next` атомарно забирает одну задачу через `UPDATE … WHERE id = (SELECT … FOR UPDATE SKIP LOCKED)`, поэтому можно запускать несколько воркеров.
- **Повторы** только для временных ошибок: сетевые ошибки Ollama (`httpx.HTTPError`) и потеря соединения с БД (`OperationalError`), до `JOB_MAX_ATTEMPTS` попыток. Битый файл или пустой текст сразу переводят документ в `failed`, а текст ошибки пишется в `ingestion_jobs.last_error`.
- **Известное ограничение:** если воркер упадёт посреди задачи, она останется в статусе `running`. Нужен периодический возврат зависших задач в очередь по таймауту `started_at`.

## Переиндексация

Нужна при смене модели эмбеддингов, размерности или алгоритма нарезки. Оригиналы лежат в `document_versions.raw`, поэтому достаточно поставить в очередь `current_version_id` каждого документа. Отдельная CLI-команда — в TODO. При смене размерности нужна ещё миграция колонки `embedding`.

## Оценка качества

Сразу после первичного импорта собирается eval-набор: 30–50 пар «вопрос → документ/чанк с ответом». Метрики поиска — Recall@k и MRR. Набор прогоняется при каждом изменении нарезки, модели или способа слияния.

Эксперименты для ВКР:
- стратегии нарезки: fixed-size / recursive / по структуре;
- только dense / только BM25 / hybrid (RRF);
- с реранкером и без;
- `ts_rank` против BM25 (`pg_search`);
- опционально: sparse-выход bge-m3 через FlagEmbedding вместо BM25.

## Запуск локально

```bash
docker compose up -d db
ollama pull bge-m3                  # Ollama на macOS ставится нативно, не в Docker
cd backend
cp .env.example .env
uv sync
uv run alembic upgrade head
uv run uvicorn app.main:app --reload         # API: http://localhost:8000/docs
uv run python -m app.ingestion.worker        # воркер, в отдельном терминале
uv run python -m app.ingestion.cli ./wiki_export --owner "Иванов И.И."
```

### Известные ограничения `submit_document`

- [ ] **Гонка дублей:** два одинаковых файла, загруженные одновременно, оба пройдут проверку, потому что на `content_hash` нет уникального ограничения. Вариант решения: `UNIQUE` на хеш и перехват `IntegrityError` → 409.
- [ ] **Гонка номеров версий:** две одновременные загрузки новой версии одного документа получат одинаковый `max + 1`, и вторая упадёт на `UNIQUE (document_id, version)` с ошибкой 500. Вариант решения: `SELECT … FOR UPDATE` строки `documents` перед подсчётом версии.
- [ ] **Откат версии считается дублем:** повторная загрузка файла прошлой версии (v1 → v2 → снова v1) отклоняется как «уже есть». Нужна отдельная операция «сделать версию N текущей».
